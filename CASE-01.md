# Case 01 — Успешный вход после серии ошибок

**Учебное расследование. Все данные синтетические.** Статус: подозрительная активность, требуется дополнительная проверка. Компрометация не установлена.

## Сигнал и охват

На `vpn-01` видны пять неудачных входов `alice` с `192.0.2.10`, затем успешный. Доступно 13 нормализованных событий аутентификации за 30 минут 30 секунд, UTC. Нет MFA, user agent, географии, endpoint telemetry и активности внутри сессии.

Исходные данные: [auth.csv](auth.csv), [context.json](auth-context.json). [Вся временная линия](01-authentication-timeline.md), [воспроизводимый finding](01-authentication-findings.json).

## Наблюдения

| События | Время UTC | Факт |
|---|---|---|
| auth-001 — auth-005 | 10:00:00 — 10:02:00 | Пять ошибок для alice, один IP и хост |
| auth-006 | 10:02:30 | Успех для той же комбинации |
| auth-007 — auth-011 | 10:10:00 — 10:11:20 | Другой IP: ошибки для пяти разных пользователей |
| auth-012 — auth-013 | 10:30:00 — 10:30:30 | Одна ошибка и успех bob с третьего IP |

Пять ошибок `alice` находятся в 600-секундном окне перед успехом. Это выполняет условие корреляции, но не сообщает, кто фактически вошёл. Второй IP демонстрирует возможный password spray; связи с первым IP в данных нет. Попытки `bob` не достигают порога; контекст содержит объяснение о неверно введённом пароле.

## Гипотезы

| Гипотеза | Что её поддерживает | Чего не хватает |
|---|---|---|
| Подбор пароля с последующим входом alice | Серия ошибок и успех с того же IP | Владение IP, MFA, подтверждение пользователя, активность сессии |
| Ошибки легитимного пользователя | Такой паттерн возможен при неверном пароле | Подтверждение alice и известное устройство |
| Общий шлюз/автоматизация для второго IP | Один IP касается разных пользователей | NAT/VPN-инвентаризация, расписание задач |
| Один общий атакующий для двух IP | В предоставленных событиях подтверждения нет | Независимые общие признаки инфраструктуры или сессий |

## Решение

Приоритет первого сигнала выше, чем серии ошибок без успеха: успешная аутентификация требует проверить последующие действия. Передать на углублённый анализ, сохранив `auth-001`…`auth-006`. Не объявлять takeover и не блокировать весь IP автоматически: он может принадлежать общему шлюзу.

Отдельно проверить второй IP на spray. События `bob` можно считать низкоприоритетными в рамках данного набора, но отсутствие порога не является доказательством отсутствия угрозы.

## Следующие действия — предложены, не выполнены

1. Запросить у alice подтверждение времени/устройства и проверить MFA.
2. Определить назначение IP по внутренней инвентаризации; публичная репутация не заменяет контекст.
3. Проверить действия успешной сессии, новые устройства и изменения доступа.
4. При подтверждении чужого входа — эскалация и отзыв сессий по процедуре организации.

## Воспроизведение

Из корня репозитория: `python replay.py --check`. Скрипт воспроизводит основной finding с шестью event IDs. Связанный [auth-log-analyzer](https://github.com/assnce/auth-log-analyzer) на том же файле выдаёт три сигнала: failure burst, success after failures и possible spray.
